# v2 구현 범위와 설계 결정

## 목표

v4.1의 L2는 저위험 안내를 승인 없이 완료하는 경로이며, L3에 해당하는 환불·보상·계정 권리 결정은 사람에게 넘긴다. 검색 성공과 자동 발송 승인을 분리하고, 실제 팀 시스템이 준비되기 전에도 로컬에서 전체 사용자 흐름을 개발할 수 있게 한다.

## 구성

React/Vite 화면 → 로컬 HTTP API → 업무 규칙/임시 RAG → SQLite 저장으로 구성한다. 화면에서는 상태를 계산하여 저장한 것처럼 표시하지 않으며, 서버가 반환한 결과를 사용한다. 업무 규칙은 순수 모듈로 분리해 기존 시연의 회귀 검사를 유지한다.

기획의 정식 서버는 FastAPI/PostgreSQL이다. 이번 v2에서는 사용자가 한 실행 환경으로 시작할 수 있도록 Node.js 24와 내장 SQLite를 선택했다. 이 선택은 팀 서버의 기술 스택 변경 제안이 아니다. 팀 API 연결 시 로컬 서버를 참조 구현으로 남기고 프런트 adapter와 RAG provider를 교체한다.

## 구현 및 연결 경계

| 영역 | v2 로컬 구현 | 정식 연결에서 필요한 일 |
| --- | --- | --- |
| 문의 흐름 | 접수·자동 안내·사람 이관·재문의 | 실제 고객 인증과 객체 권한 |
| 초안/승인 | 초안 수정, 승인 무효화, 만료·본문·회차 검사 | 팀 승인 저장 모델·직원 권한과 연결 |
| 후속 | 등록·담당·기한·공개/내부 메모·상태 | 팀 후속 인수·팀 권한 계약으로 변환 |
| 자동화 제어 | 중지·회귀 검사·명시적 재개 | PostgreSQL generation·worker 확정 fence |
| 임시 RAG | 문서 로드·무결성 검증·실제 검색·근거 응답 | 승인된 corpus·정식 검색·모델 평가 |
| 데이터 저장 | SQLite 원자 저장·revision 충돌·멱등성 | 팀 DB transaction·lease·outbox |
| 고객 화면 | 공개 projection과 본인 합성 문의 | JWT와 실제 고객 scope |
| P1/P2 | 기존 합성 집계·제안·탐지 유지 | Fabric 게시 배치와 실시간 모델 |

회차마다 최종 응답은 한 번만 남기며, 중복 요청과 오래된 화면의 쓰기를 구분한다. 검색 결과는 근거이지 자동화 허가 자체가 아니다. 정책 변경, 주문 소유권·조회 신선도, 사람 요청, 미완료 후속, 자동화 중지를 최종 판단에서 확인한다.

## 합성 데이터 원칙

운영 문의는 독립 v2 합성 데이터이다. 제품 분석은 이전 검증 fixture를 그대로 사용하며 운영 문의 원장과 동일한 모집단이라고 표현하지 않는다. RAG 문서는 새 개발용 정책이며 실제 쇼핑몰 약관·법률·환불 보장으로 제공하지 않는다. 기존 30개 합성 정책과 공식 참고자료 73개의 승인 상태를 변경하지 않았다.
